# Обновление существующей базы

`schema.sql` предназначен для создания новой схемы. Для существующей базы
изменения применяются отдельными SQL-миграциями без пересоздания таблиц.

## 001 — единица измерения «сутки»

Если сохранение ресурса завершается ошибкой `22P02: invalid input value for enum
unit_type: "day"`, в PostgreSQL отсутствует значение, которое уже поддерживает backend.

Из корня репозитория CampLink-DataBase выполните от владельца типа:

```bash
psql -h localhost -U postgres -d camplink -v ON_ERROR_STOP=1 -f SQL/migrations/001_add_day_unit_type.sql
```

Укажите адрес и имя именно той базы, к которой подключён backend. Миграция
сохраняет существующие данные; повторный запуск допустим. Выполняйте её отдельно
от операций, использующих новое значение: оно доступно после фиксации транзакции.

Проверьте результат:

```sql
SELECT unnest(enum_range(NULL::public.unit_type));
```

Ожидаемые значения: `piece`, `kg`, `liter`, `hour`, `day`.
После успешного применения повторите сохранение ресурса с `unitType: 4`.

## 002 — суточный учёт без часовых записей

Обязательная миграция перед запуском backend с новым суточным учётом:

1. Остановите все экземпляры backend и сделайте резервную копию базы.
2. Если в `unit_type` отсутствует `day`, сначала примените миграцию 001 отдельно.
3. Проверьте, что прежние `timestamp without time zone` записаны в UTC.
   Миграция интерпретирует их как UTC. Если исторические значения записывались
   в местном времени, сначала нужен отдельный согласованный план преобразования.
4. Из корня CampLink-DataBase выполните от владельца таблиц:

```bash
psql -h localhost -U postgres -d camplink -v ON_ERROR_STOP=1 -f SQL/migrations/002_daily_accounting.sql
```

Скрипт выполняется одной транзакцией с блокировкой изменяемых таблиц. Он добавляет
`inventory.booking_line_id` без FK, делает времена позиции необязательными,
приводит временные колонки к `timestamptz` и создаёт индексы уникальности дневных
остатков и расходов по позиции. Для суточных ресурсов устанавливает кратность 1.

Чистые полные наборы из 24 часов сворачиваются в одну строку. Количество и цена
не суммируются. Оплата и статус расхода сохраняются; остатки получают статус
«подтверждено». Все исходные суточные записи сохраняются в таблицах
`inventory_before_daily_accounting`, `booking_line_before_daily_accounting`,
`resource_before_daily_accounting` для сверки и восстановления по резервной копии.

Неполный день, разные значения внутри суток, неопределённая связь с позицией
или многодневная позиция останавливают миграцию с полным откатом. Такие записи
нужно сверить отдельно; скрипт не выбирает значение и не удаляет их произвольно.
После ошибки в интерактивном SQL-клиенте выполните `ROLLBACK`.

Если ошибка сообщает о неоднозначной суточной истории, после `ROLLBACK`
запустите `002_daily_accounting_diagnostics.sql`. Это скрипт только для чтения:
он показывает проблемные ресурсы, даты, ID записей и конкретные причины отказа.
Он работает и до добавления `booking_line_id`. Второй набор результатов
показывает позиции бронирования с неполным или многодневным интервалом.
Посмотрите оба набора данных в SQL-клиенте. Результат нужен для выбора
способа сверки; отсутствие строк не проверяет все условия миграции,
например однозначность связи расхода с позицией.

Проверка после успешного применения:

```sql
-- Должно вернуть 0.
SELECT count(*)
FROM public.inventory i JOIN public.resource r USING (resource_id)
WHERE r.unit_type = 'day' AND i.reserved_time IS NOT NULL;

-- Суточные записи и ссылки на конкретные позиции бронирования.
SELECT i.inventory_id, i.resource_id, c.date, i.booking_id, i.booking_line_id,
       i.movement_type, i.operation_type, i.quantity, i.price
FROM public.inventory i
JOIN public.resource r USING (resource_id)
JOIN public.calendar c USING (calendar_id)
WHERE r.unit_type = 'day'
ORDER BY c.date, i.resource_id, i.inventory_id;
```

Затем запустите новый backend и обновите фронтенд. Миграция допускает повторный
запуск; архив не перезаписывается. Не запускайте старую версию backend после
перехода: она создаёт почасовые расходы для суточных ресурсов. Финансовые отчёты
за исторические оплаченные сутки нужно сверить с архивом: прежний расчёт мог
ошибочно учитывать суточную цену 24 раза.
